# TUI: show the name of the agent session of a run, kept in the journal

## TL;DR

- The name of the agent session is stored in the journal, so the TUI never opens a transcript. Two writers: the executor record of a run start, a served step and a completed step gets `executor.session_name`; and the agent-log pass (every `interval_s`, 10 s by default, and at each step end) journals a new event `agent_session_named` when the name of a session proven to belong to the run has changed, so a `/rename` shows without a tool call.
- The list of runs shows the session name instead of the slug (the slug when there is none); a name that is only a guess carries a dim `?`; rows with the same name show `name · <end of the run id>`. The band (`headerBand`) and the card (`cardLines`) keep the slug and add `session «name» · id`. A gate confirmation shows the slug, the end of the run id and the row's label.
- What the fifth critique changed: the label people pick a row by is agent-influenced text, so the clash rule is stricter (case and compatibility folding; a name equal to any other row's slug or label is a clash) and the confirmation shows what the agent cannot write (the run id end); the `indexPath` fix leaves this task; the model scan keeps its existing logic (the pre-check is for the name only); the event record carries no hash (the state keeps it); the card journal hides the event; wide characters are measured by columns for the new label; the tests are specified (proven-session helper, cheap cap test, behavioural no-transcript test, refutations tied to tests).
- Cost: a stored-data change under rule 5 (a v2-only event, a capability, hashes in the opaque `agentLog`). Three commits in one run; the event commit is droppable. Risks: names are personal text in the journal; the list loses the slug on a clash; the event is fresh only while a pass runs.

## Decisions needed

1. **Rule 5 asks for a real fixture; the README exception ("an addition only a newer run carries needs no new directory") does not clearly cover a new event kind written into runs in flight.** (a) Recommended: no new fixture directory; a hand-built v2 journal pins the event, and commit 1 adds a test that the current engine (`status`, `report`, the next step, `kodel wait`, the TUI load) treats a journal with an unknown event as if it were absent, so "an older engine ignores it" is shown, not claimed. (b) A real fixture directory: the script must turn `history.agent_log` on, write a fake transcript that holds a call of the run's tools, and the guard test that rejects a `session` value in a fixture must be relaxed. If no answer: (a).
2. **Confirmations.** The row is chosen by an agent-influenced label, so a look-alike name could steer a gate decision to the wrong row. (a) Recommended: the confirmation shows `Approve «slug» · <last 8 characters of the run id> · row «label»` (the id end is not the agent's text; the label is shown so a mismatch is visible); notices and pipeline-change titles stay as they are. (b) Leave confirmations as they are. If no answer: (a).
3. **The list on a clash.** One session usually drives many runs, so many rows will read `name · <run-id end>` and the slug (the task) is not in the list; the card has it. (a) As chosen: `name · run-id end`. (b) `slug · run-id end` on a clash (the name is lost there). If no answer: (a).
4. **`indexPath` fix** (`executorContext()` never passes the hook index path, so with `storage: home` and no env session later records find no hook session; it also widens the guessed sessions): moved out of this task into its own task. If no answer: moved out (I create the task with `task_create` when you say so).
5. **Numbers I chose** (you gave none): name cut at 120 characters; 8 characters of the run id. Answered by the person: name events are not capped (no 200-event or 50-session limit); the only bound is one event per session per pass and only when the hash of the name changed.
6. **Scope**: the TUI list only; `kodel status` unchanged (reworked later); the list shows the newest session's name per run (the list of all sessions is TASK-8FEG). If no answer: as stated.

Settled by the person: every name is written whenever `history.executor` is on; the list shows named sessions, guesses marked; equal names show the run id; one run; the dedicated event. Choices inside: the event needs `history.executor` and `history.agent_log` on and is written in `metadata` mode too; the order of the three commits.

Accepted limits (also in `docs/history.md`): a rename is journaled only while a pass runs: the run is `running` (a paused or finished run keeps its last name), the server holding the ticker is alive and has seen a call of the run since it started (after a restart, `/resume` or a Claude Code restart nothing is journaled until the agent calls), `interval_s` is not 0, and fewer than 4000 `agent_log_saved` events were journaled (the tick cap counts saves, not time; a step end still runs a pass); with `storage: home` the pass sees only the session of the server's environment; the name is found only in the last 512 KB of the transcript (renamed sessions repeat it every few KB; an automatic session is checked on a real transcript at implementation); no transcript, no name; a cleared title is not journaled; an unnamed proven session has no event and keeps `?` if its id was a guess; the current session is the newest of the agent's recorded calls, so after `/clear` or `/resume`, with `history.prompts` off (no `step_served`), or with workers on different servers, the label can lag or flip between sessions; a run's name is a snapshot at its last pass or call (two runs of one session may show different names after a rename); names of guessed sessions, possibly another window of the person, are written too; an older kodel and an older TUI count a name event as activity; every named proven session gets one event per new run on its first pass (the event is what proves it). Out of scope (TASK-8FEG): the list of all sessions, the search, choosing the current session from the proven ones.

## Behaviour change

- **List of runs**: the row shows the name of the newest session of the run when it has one (a dim `?` after it for a guess), else the slug. Two rows clash when their labels are equal after compatibility folding (NFKC) and case folding, or when a label equals another row's slug or label; every clashing row shows `name · <last 8 characters of the run id>`, the name shortened with `…` (width counted in terminal columns) to keep the id. A run whose state cannot be read keeps its slug.
- **Top of a run's card**: the title keeps the slug; below it a dim line `session «name» · a1b2c3d4` (id cut to 8), `(maybe)` after it for a guess. No name: `session a1b2c3d4`. No session recorded: no line. In the band: a line after the title. In compact mode (`height < 22`): no line is added; the first line shows `session «name» · id` where it showed `id · pipeline`. Widths of the new text are counted in columns, so emoji and CJK do not push the tag and time off a row.
- **Confirmation** (Decision 2): `Approve «slug» · <id end> · row «label»`. Notices and pipeline-change titles are unchanged.
- **Which session**: the newest `run_started` / `step_served` / `agent_completed` record with a valid `executor.session`, file order. **Which name**: the newest non-empty name for that session id, from an executor record or an `agent_session_named` event, file order; an event for another (older) session does not change the row. **The mark**: `?` / `(maybe)` unless the session's source is `observed-env` or an `agent_session_named` event names that id (proven).
- **Journal in the card** and the quiet detection ignore `agent_session_named` (no raw event name in the card; a rename does not make a stuck agent look alive). `status` and `report` output is unchanged for finished runs; for a running run `report`'s last record may be a name event.

## Risks and invariants

- **Stored data, rule 5.** (1) `session_name` inside `executor`: optional, passes both codecs, compatible. (2) A new journal event `agent_session_named` (`session`, `name`): v2-only (`V2_ONLY_EVENTS`; `encodeV1Record` refuses an event format 1 does not list), a capability `sessionNames` (added to `V1_CAPABILITIES` false, `V2_CAPABILITIES` true, to every table that lists capabilities and to `docs/run-formats.md`), asked by the pass and by the handler (a format that cannot hold it makes the handler a quiet `Repeat`), and an optional `nameHashes` inside the opaque `state.agentLog`. The event decides no step: an engine that ignores it decides the same; an older engine that rewrites `agentLog` and drops the sub-keys only makes the newer one journal a duplicate name; an older reader ignores the unknown event (pinned by Decision 1's test). Rule 5's fixture is answered by Decision 1. A decision id for the event is recorded in the local notes by the implementer; the tests carry `t41_` for the format work and each refutation is tied to a named test below. `docs/run-formats.md` says what a run in flight does (format 1 unchanged; a format-2 run started before gets names from now on; an older kodel counts the event as activity); `docs/history.md` gets the field, the event, every limit above, that the name is display text chosen by the person or the model (not the agent's word, unlike `model`), and a line for projects whose history is already committed: new records carry names, `history.executor: false` stops it, nothing is rewritten.
- **Principle 3**: `state.json` is not redacted, so it holds no text: only `sha256` of the cleaned, then redacted name, kept in `agentLog.nameHashes` (the hash is taken after redaction so a change of rules cannot produce a duplicate each pass). The event record holds the name only (the store redacts it) and no hash. Test: a unique marker string never appears in `state.json`.
- **pipeline-core stays pure**: the `ExecutorRecord` type, the `RunEvent` and handler, `cleanSessionName`, the capability. Hashing and the transcript are in `packages/local`. Kodel Server never emits the event; its journal and state schemas (a typed `agentLog`, an exhaustive switch over `RunEvent`) and any import of local journals must allow the new members: noted for the PR, with a Server-like exhaustive switch in this repository's typecheck.
- **Agent input is untrusted** (principle 1) **and humans decide** (principle 6): the name is display text; it decides nothing. It is cleaned with `cleanSessionName` (control, bidi U+202A-202E and U+2066-2069, zero-width out; cut at 120; `cleanExecutorText` stays untouched), redacted with the host's rules, cleaned again by the TUI reader, and drawn through `fit` and the final neutralizing. The row label is agent-influenced, so a gate prompt shows what the agent cannot write (Decision 2); homoglyphs across scripts (Cyrillic vs Latin) are not folded, which the run-id end in the confirmation answers.
- **Session id guard**: the name scan refuses an id that fails `SAFE_SESSION` of `session-finder.ts` (128 characters) before it touches a path; `observe`'s guard and what it records are unchanged.
- **Cost**: the model scan keeps its logic (parse from the end until the first assistant line); the name scan checks each line of the 512 KB tail with `includes('"custom-title"')` / `includes('"agent-name"')` and parses only those. In the pass the name of each proven candidate (at most 21) is read once through the size+mtime cache (only the running session's file misses), the apply takes `lock.stillHeld()` like the copy does, and both are inside the pass's time budget; at a step end they add that to `pipeline_complete_step`. The journal grows by about 150 bytes per record with a name; name events are not capped (one per session per pass at most, only on a change). The TUI adds one pass over records it already reads.
- **Fail closed**: an unreadable transcript gives no name; a failed apply never fails the pass or a call. **Principle 4**: no I/O in pipeline-core. Format-1 runs are byte-identical.
