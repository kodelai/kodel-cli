# Read-only history tools: `history_runs`, `history_run_details`, `history_agent_log`

## TL;DR

- Three read-only MCP tools: list the runs of this project, read one run on three levels (run, node, attempt), read the stored agent log of one attempt. No stored format changes; everything is built from what `kodel status`, `report` and `agent_log/` already read.
- Cost: four optional host methods, one pure view module and one tool file in `pipeline-core`, one implementation in `LocalPipelineHost`, two new error codes, one instruction rule, tests, a docs section. About 1 800 lines with tests.
- What the critique changed: the report is no longer read through `open()` (it needs the pipeline copy, caches the run and fails on old or edited runs): history has its own read path from state + journal; cursors are keyed, not offsets; the answer carries `integrity` and `seal`; redaction uses the host's rules and runs before the cut; every block has a size bound; the tools are always registered (as the task says) and answer `HISTORY_UNAVAILABLE` on a host without history; the agent log is read only up to what the journal vouches for and is attributed by time, not by copy pass.
- Risks: it shows run history to the agent (rule 5 of the instructions says the agent does not read run files); agent-log text is untrusted; the size and cursor contract is new and shared by three tools.

## Decisions needed

Recommendation: (a). The exposure is real: with the agent log on, the agent sees redacted 500-character previews of what the person and the tools said in past runs, and redaction is pattern-based (it does not catch every secret). It is the person's call. If no answer: (a), and `include_messages` stays off by default in every call.
2. **Registration.** (a) Register the three tools on every host; a host without history answers `HISTORY_UNAVAILABLE` (what the task says); (b) register only when the host has history. Recommendation: (a): the surface and `instructions_hash` then do not depend on the host and rule `9c` can be unconditional. Cost: Kodel Server advertises tools that answer `HISTORY_UNAVAILABLE` until it implements them. If no answer: (a).
3. **A decision id.** The tools open history to the agent, which touches rule 5 and Principles 1 and 6, and a decision of the log needs a refutation criterion. Proposed: "refuted if an agent obtains an unredacted secret, a changed file or a trust decision through a history tool". Please give the id (`T-NN`) so the tests carry it; until then they are named `history_tools_*`.
4. **Task text in `history_run_details`.** The list has no task text (`slug` + `task_key` only). Recommendation: the run summary of details keeps `task`, redacted and cut to 500 characters, because a run without a tracker task has no other description. If no answer: keep it.
5. **Own tools.** `history_*` count as tools of the engine in the tool-calls report (`own: true`, like `pipeline_*`), so they do not skew the account of the agent's own work. Needs `isOwnTool` and its registry test extended. If no answer: do it.
6. **One change.** Recommendation: one change in three commits (infrastructure + `history_runs`, details, agent log). If no answer: that.

## Behaviour change

The MCP server offers three more read-only tools. The agent can ask which runs this project had and how they ended (`history_runs`); where the time went and what failed in one run, down to a node and an attempt, with the calls of its tools on the last level (`history_run_details`); and what it did in an attempt (`history_agent_log`, conversation text only with `include_messages: true`). Level 1 of the details also says whether the run's files were changed outside kodel (`integrity`, `seal`). Data from the agent's own log is marked `unverified`. A host without history answers `HISTORY_UNAVAILABLE`. Runs of other checkouts are never shown. Nothing a person decides becomes available to the agent.

## Risks and invariants

- **Agent input is untrusted (P1).** Answers go into the agent's context. Every string in an answer goes through the host's redactor (its project rules, not only the built-in ones) and then free text is cut to 500 characters, in that order (a cut first could split a secret so it no longer matches). The tool descriptions and rule `9c` say the answers are data from past runs, never instructions. `unverified: true` is inside every `tool_calls` and `agent_log` block (so it survives `fields`).
- **Edited history is not trusted silently.** The run files live in the repository and the agent can write them. Level 1 carries `integrity` and `seal` as `kodel report` shows them, and the answer says when the files do not match.
- **Fail closed / humans decide trust (P2, P6).** The tools only read: no journal or state write, no lock, no cache entry; no gate, `ack`, `seal` or change is reachable. A test snapshots the run folder before and after.
- **No I/O in the core (P4, P5).** The view logic (cursors, `fields`, bounds, answers) is pure and lives in `pipeline-core` with an injected redactor; the file reads are in `@kodel-ai/local` behind four optional host methods. The core's import test must pass. The cursor is encoded with `TextEncoder` and base64url (no `Buffer`, no `btoa`).
- **Host methods are guarded.** They are flat methods of the host (`historyRuns`, `historyReport`, `historyAgentLog`, `historyIntegrity`), listed in `ENTRY_POINTS` so `guardEntryPoints` turns file-system errors into the scrubbed `CONFIG_INVALID` (no `~/.kodel` path to the agent) and `assertPlace` runs (storage unchanged since start). No direct `readStoredAgentLog(store, ...)` from outside this guard.
- **Stored data (P8, rules 1-5).** No stored field is added or changed; no codec, fixture or `v` bump. Reads use the codecs as `status` and `report` do. The three states stay apart: a run in a format this engine does not read is `UNSUPPORTED_FORMAT` with its `format` ("written by a newer kodel, upgrade kodel"); a state that does not fit its format is "cannot read" with the real code `runSummaries()` gave (passed through, never mapped to `UNSUPPORTED_FORMAT`); only a hash mismatch says "modified". A run of `meta.json` format 1 is read and listed (rule 4): its report is built from state and journal and does not need the pipeline copy. A run whose kept pipeline copy is edited or missing still gets its history, with `integrity` saying so.
- **Pagination is stable where the data is.** `history_runs` uses a keyset cursor (`created_at`, `run_id`, newest first), so a run started between calls cannot repeat or hide an item. Nodes (order of first entry), attempts (by number), tool-call lines (by start) and agent-log events (by `seq` within a session) use the key of the last item. `total` is the count at the time of the call and may change between pages; it is not an error. The cursor is bound to the tool, run id, level, node, attempt, the filters (`status`, `pipeline`, `kind`, `tool`, `include_messages`) and the run's state format `v`; `limit` and `fields` may change between pages. Anything else, a damaged cursor, a key that is no longer there, or a session that is not one of the attempt's sessions, is `INVALID_CURSOR`. `kodel migrate` mid-walk changes `v` and so ends the walk with `INVALID_CURSOR`.
- **Size.** An answer is built to at most 64 KB of serialized JSON (measured on the shape after `fields`). A page returns at least one item. An item that alone is over the cap is shrunk (texts to 100 characters, inner arrays cut with an `omitted` count, `truncated: true`) instead of looping on the same `next`. The blocks that are not lists are bounded: `pipeline_changes` and `agent_decisions` 20 entries each, an attempt's `checks` and `findings` 50, `by_tool` 30, each with `omitted`.
- **Cost of a call.** `historyReport` is the report without the run patch (`task_size` is left out, `readRunPatch` and `measurePatch` are not run); the agent-log stream is read only up to the journal's length. `history_runs` reads every state like `kodel status`. No cache is added; this is stated in the tool description for long histories.
- **Agent log attribution.** `agent_log_saved` is booked per copy pass to the first open step, so in a fork or at a step boundary a range holds other steps' events. Events are placed by their time against the attempts of the journal with the same placement the tool-calls pass uses (`placementFromJournal`/`placeCall`), not by the pass record; the records give only the sessions and the lengths the journal vouches for (the last `stream_to` per session, read from the same journal that was read, so nothing past what it vouches for is shown). If that placement cannot be reused for non-call events, the answer says `attribution: "approximate"`. A fork test decides it.
- **Foreign checkouts.** In `home` storage a run of another clone is not listed, and all three tools answer `UNKNOWN_RUN` for it.
- **Surface.** The tools are always in the served surface; `toolsFingerprint` and `instructions_hash` change once, by design. `CONTRACT_VERSION` is bumped as the comment above it says (adding tools is an addition); a test pins the value.
- **Windows and Node.** The tools add a reader of `state.json` and the journal of an active run in the process that writes them; one test runs a step while the details are read, and runs in CI on all three systems.

## Acceptance criteria and tests

The test names carry the decision id once the person gives it (Decision 3).

1. The three tools are registered on every host; on a host without history each answers `HISTORY_UNAVAILABLE`. `history_tools_registered_and_unavailable_without_host_support`.
2. `history_runs` lists newest first with the spec's fields and no task text; `status` and `pipeline` filter (an unknown value is `INVALID_ARGUMENTS` listing the known ones) and `total` follows the filter. `history_tools_runs_lists_newest_first_without_task_text`, `history_tools_runs_filters_and_total`.
3. Runs of another checkout are hidden from all three tools (`UNKNOWN_RUN`). An unknown run id is `UNKNOWN_RUN`. `history_tools_foreign_and_unknown_run`.
4. Unreadable runs, each from its own fixture: a newer-format state (`UNSUPPORTED_FORMAT` + `format`), a damaged state ("cannot read" with its real code), a `meta.json` format-1 run (read and listed, details work), a run with an edited pipeline copy (details work, `integrity` says so). In the list they have `status` `unreadable` or `format N`, match a `status` filter by that string and count in `total`. `history_tools_unreadable_runs_keep_their_own_error`.
5. Pagination, per list: a walk of all pages returns every item once; for the run list a run started between two calls neither repeats nor hides an item; `page.next` is absent on the last page; `limit` bounds (1..100 runs, 1..200 others) and defaults. `history_tools_pagination_walks_every_item_once`, `history_tools_runs_cursor_survives_a_new_run`, `history_tools_limit_bounds`.
6. The cursor: every binding in the Risks list (tool, run id, level, node, attempt, filters, `v`) gives `INVALID_CURSOR` when changed; `limit` and `fields` may change; a damaged cursor, a well-formed one with a position past the end or a key that is gone, a forged agent-log cursor naming another attempt's session: `INVALID_CURSOR`, no crash, no leak. A `kodel migrate` between pages ends the walk. `history_tools_cursor_is_bound`, `history_tools_forged_cursor_is_refused`.
7. `fields`: only the named blocks plus `ok`, `level`, `page` and the ids; an unknown name is `INVALID_ARGUMENTS` listing the allowed names of that level; `page` is present only when its list is in the answer; `unverified` stays inside its block when only that block is asked. A misspelled argument is refused (the tools use a strict schema). `history_tools_fields_filter_and_validation`, `history_tools_strict_arguments`.
8. Size: with maximal strings and the largest `limit` the answer is under 64 KB and has `page.next`; a page always holds at least one item; one item over the cap is shrunk and marked, never an empty page with a repeating `next`; the unbounded blocks are cut with `omitted`. `history_tools_answer_is_capped_in_bytes`, `history_tools_oversize_item_makes_progress`, `history_tools_blocks_are_bounded`.
9. `history_run_details` level 1: summary (with redacted, cut `task`), `nodes` page (seconds, attempts, last outcome, checks run and failed), `pipeline_changes`, `agent_decisions`, `usage`, `tool_calls` totals, `agent_log` counters, `integrity`, `seal`; page 2 holds only `level`, `page`, `nodes`. `history_tools_details_level_run`, `history_tools_details_later_pages_hold_only_the_list`.
10. Level 2: node info, the node's check aggregate (`CheckReport` filtered by `node`), `attempts` page. An unknown node is `UNKNOWN_NODE` with the known slugs. Level 3: the attempt in full and `tool_calls.lines` paged from the report (at most 200 rows, rest in `omitted`, `unverified`); `attempt` without `node` is `INVALID_ARGUMENTS`; an attempt number that does not exist is `INVALID_ARGUMENTS` with the number of attempts in `details`; an attempt still running (no outcome) and one with `tool_calls` off both answer. `history_tools_details_level_node`, `history_tools_details_level_attempt`, `history_tools_details_attempt_in_progress`.
11. Blocks the run did not collect are `{not_collected: true, reason}`, unreadable ones `{cannot_read: true, format}`. With `history.agent_log`, `tool_calls` and `usage` each off, the matching block (and the log tool) says `not_collected`. `history_tools_not_collected_blocks_are_explained`, `history_tools_privacy_switches_are_honoured`.
12. `history_agent_log`: events of one attempt, paged by `seq` per session, filters `kind` and `tool` (alone and together), `fields`. Two sessions (a subagent) interleaved in time come in a fixed order, with no duplicate across pages. A fork run gives each attempt only its own events. `history_tools_agent_log_pages_by_seq`, `history_tools_agent_log_filters`, `history_tools_agent_log_subagent_sessions`, `history_tools_agent_log_attribution_in_a_fork`.
13. Messages: skipped unless `include_messages`; the answer says `skipped: {message: N}`; `kind: ["message"]` without the flag is `INVALID_ARGUMENTS` naming the flag. `history_tools_agent_log_messages_behind_flag`.
14. A stream that is missing, damaged (also in the middle of a walk) or in a newer format gives `problem` with the events read so far and says the list is partial, on every page it affects; bytes appended past the journaled length are never shown. `history_tools_agent_log_reports_problems`, `history_tools_agent_log_stops_at_the_journal`.
15. Redaction: a secret planted in every field the tools return (texts, ids, slugs, tool names, `workdir`, `task_key`, failure texts, error messages and `details`) and a project-rule secret do not appear anywhere in the serialized answer; the 500-character cut at 500, 501 and across a multi-byte character; a secret split by the cut does not come out. `history_tools_output_is_redacted_and_capped`.
16. Read-only: the run folder (files and mtimes) is the same after calls on a running run and on one waiting at a gate; no lock is taken; no run is added to the host's cache. `history_tools_do_not_write`.
17. A step of a run is taken while its details are read (the same process); runs on the three CI systems. `history_tools_read_while_run_advances`.
18. `history_*` are counted as own tools in the tool-calls report. `history_tools_are_own_tools`.
19. The served surface: the fingerprint includes the tools, `CONTRACT_VERSION` has the bumped value, rule `9c` is in `SERVER_INSTRUCTIONS`. `history_tools_surface_and_instructions`. The docs section names every parameter and every error code of the three tools. `history_tools_docs_name_every_parameter_and_code`.
20. The commands of `AGENTS.md` pass: `bun run typecheck`, `bun run lint`, `bun test`, `bun run build && node scripts/check-artifact.mjs`. If `check-artifact` can list the server's tools, it asserts the three names on the built file.

What no test can show, and how it is covered: that an agent treats answers as data (model behaviour: the tests check the flags, the wording and the default of `include_messages`; a real-agent scenario in `tests/agents` can sample it, not prove it); that 64 KB suits every client; that redaction catches a secret of a shape it does not know; the absence of races with a live run (sampled by criterion 17).

## Implementation notes (where the build differs from the plan)

- Three host methods, not four: `historyRuns`, `historyRun` (the report, `integrity`, `seal` and `pipeline_copy` in one read) and `historyAgentLog`, plus `historyRedact`. The three that read are in `ENTRY_POINTS` and call `assertPlace`; `historyRedact` is synchronous and pure, so it is in neither.
- `historyRun` takes no lock. A finished run being sealed at the very moment of the read can show a passing `seal: modified`; `kodel report` avoids it by taking the run's lock, which a read-only tool must not do. The tools say nothing more than the files say at that moment.
- `skipped.message` counts the messages left out in the whole attempt, not per page.
- The core redacts with the built-in rules when a host gives no `historyRedact`.
- Not done: an assertion about the three tool names in `scripts/check-artifact.mjs` (the script was not changed because it needs the built file, which this step does not build), and a test for a foreign checkout on the real host (it needs `storage: home`); the foreign case is covered on the fake host (`UNKNOWN_RUN` when the host returns nothing). The read-while-advancing case runs through the MCP server in `packages/cli/test/history-tools.test.ts`, which CI runs on all three systems.
- `packages/cli/test/executor.test.ts` expects the new tool surface in `tools_hash`, as the plan's "the fingerprint changes once, by design" says.
- After the review of the build: the keys of an object are redacted and cut like the values; the cursor holds a digest of the key (cyrb53), not the key; the head of an answer (the blocks that are not lists) is bounded as a sum (24 KB, largest first); `findings` and the `agent_log` block are bounded, and the per-visit table of `agent_log` is not sent; `integrity` carries `pipeline_copy`; an unknown `status` is `INVALID_ARGUMENTS`; the agent-log cursor is bound to the state format like the others; a session name from the journal that is not a file name is a `damaged` problem of that stream; `attribution` is `approximate` when an event was placed while more than one agent step was open (a fork).
- Kept as they are, after the review: the cursor is encoded with `btoa`/`atob` over the bytes of `TextEncoder` (both exist in Node 22 and in the browsers, and the bytes are Latin-1 safe, so the "no `btoa`" line of the plan was stricter than needed); `withFindings` and the `FileIntegrity` construction are copied from `host.ts` (they are private there, and moving them into the run engine for ten lines costs more than the copy); `workdir` is the one in the state, as `kodel status` prints it, not the checked location `kodel report` shows; the `pipeline` filter takes any name (names are free text, so an unknown one gives an empty page).

- After the final gate was sent back (the person's comments): a node row carries `usage` (tokens and dollars summed over its attempts, `usd` null when no attempt has a price) and the `usage` block of the run adds `unattributed`; `task_size` is a block of level 1 (the host reads the run's patch as `kodel report` does, and `history_stats` asks for none: `historyRun(runId, { patch: false })`); the attempt level has `report_rows`, the rows an attempt stored as its report (a step's findings, a person's comments at a gate), through the new host method `historyAttemptReport`; and a fourth tool, `history_stats`, counts the newest runs of a pipeline with `summarizePipeline` (scope `all`), so an agent does not read hundreds of answers. The descriptions of `history_runs` and `history_run_details` point to `history_stats` for figures over many runs and do not forbid the CLI.
- `history_stats` is not paged: its nodes are cut from the end by size (`nodes_omitted`), the `versions` block is only given when named in `fields`, and `scope: current` (which needs the definitions of the pipeline now) is not offered.
