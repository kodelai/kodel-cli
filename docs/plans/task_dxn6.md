# TASK-DXN6: decide a gate from the TUI with the same checks as `kodel gate`

## TL;DR

- `a` / `r` in `kodel tui` (project mode) approve, reject or resume for real, after a confirmation inside the TUI. `--demo` keeps its simulated decisions.
- The checks of `kodel gate` / `kodel resume` move into `packages/cli/src/gate-decision.ts` in two phases: `prepare` (the command's checks, facts, ordered questions) and `commit` (the write). The command and the TUI call the same two functions. The TUI turns on an option of `commit` that **re-checks at write time** (the question may stay open for hours); the command does not, so its first commit is a pure refactor.
- Your answer to the first review: a **picker inside the run** lists all waiting gates and pauses; `a`, `r`, `c` act on the picked one by node slug and attempt.
- Cost: about 12 files, no stored-format change, no new journal field, no new dependency, nothing in `pipeline-core`. Medium to large; the TUI half is the larger one.
- What the critique changed this round: the write-time re-checks are TUI-only (the command stays as it is, no stricter `kodel gate`); comments are re-checked at write; attempts of the picker are read from one state; the quit path tracks every decided `(run, node)`; named test seams (refresh interval, quit limits, hook between check and `y`); guard tests cut from 17 to 16 and folded.

## Decisions needed

1. **Picker inside a run — decided by you.** Entries: the gate `inspect()` names first, then its `also_waiting` (gates and pauses), with the attempt of a gate read from the same state. `g` / `G` move the pick (in list focus, and in card focus when no diff is open; the implementation takes other keys if they collide); the card head says `decision 2 of 3`, the list row `· 3 decisions`. `a`, `r`, `c` act on the picked one. `also_waiting` carries the prompt but not `instructions` / `result_spec` of a gate that is not first: its card shows the prompt and the engine's facts (option a, recommended, tested); option b adds those fields to the core's answer. If unanswered: a.
2. **Pauses — decided by you (A).** A paused branch of a waiting run is a picker entry, resumed by `a`. Limits that stay: only a whole-run pause is `waiting` (`next-step.ts:605-606`); a run shown as running (a paused branch beside a moving one) has no `a`, and the card names `kodel resume <run> --node <slug>`. `Session.decisions` is empty for `pipeline_edit` and `hand_edit` heads, so the gates behind a pending change are not offered.
3. **Quit while engine work runs — decided by you (minimal).** The performer keeps a set of `(run, node)` registered when `commitGateDecision` **or** `commitResume` starts; `q` / Ctrl-C waits (`waitForRest(ms, node)` per pair, then `run.settle` per run) up to the limit of `kodel gate` (`WORK_WAIT_MS`), telling that the work may grow; a second `q` awaits the apply queue for a short deadline and calls `host.stop()` with the kill grace, and says the step **will be started again by the next caller**. No SIGINT / SIGTERM / SIGHUP handlers (stated limit).
4. **Split — decided by you.** One run, two commits; with this round's change the first is a pure refactor of `gate`/`resume` with their tests unchanged.
5. **Write-time re-check — needs your call.** The TUI's question can stay open for hours, so `commit(…, { recheck })` in the TUI refuses at the write unless: the gate at `node` is still `human` with the attempt picked; no blocking pipeline change; the pause is still there (resume); the comments are the ones shown and a rejection without a typed reason still has some; and the files are not worse than shown (a different set is refused except under the shared-tree note, as in `elicit.ts`; this part uses an exported fingerprint). Options: (a) the TUI only, the command unchanged (recommended: a pure refactor, no stricter `kodel gate`); (b) the command too, with a note in the release text and command-side tests; (c) cut the "files worse" part and keep the other four. If unanswered: (a).
6. **One line each.** No `T-` id exists for the TUI: tests use the prefix `task_dxn6_` (stated in the PR). `--ignore-pending-change` is not offered in the TUI. The notice for `hand_edit` / `pipeline_edit` is reworded because "comes later" would be wrong next to working keys. The copies of the checks in `elicit.ts` and `agent-decisions.ts` stay.

## Behaviour change

A run that waits for a person shows its decisions: one gate, or several gates and pauses of a fork. The picked one is named in the card head; `g` / `G` move the pick; the pick stays through refreshes and moves with a notice to the first decision left when its decision is gone. `a` on a gate shows what the command prints: files changed since the gate, the comments recorded at the step that go back with a rejection, the foreign-checkout sentence (as part of the question, with "the work after the decision runs in this checkout"), and, for an approval whose changes could not be checked, a second `y`. `r` is the same; without recorded comments a reason is typed first (the TUI trims what is typed; empty is none; `Esc` writes nothing). `a` on a picked pause resumes it with more attempts (a run of another checkout is refused, as the command does). Comments (`c`) go to the picked gate. After the write the notice says what happened and the list and card are read again at once; the agent's next `pipeline_next_step` sees it. Every refusal the command gives is a plain notice, nothing is written. The journal gets the same `gate_decided` / `run_resumed` record. A project-mode screen without the decision functions says "cannot decide here". `kodel gate` and `kodel resume` behave as today.

## Risks and invariants

- **Humans decide (Principles 1, 6).** Reachable only from `kodel tui`, which starts behind `requireHuman()` (checked once; the TUI is the person's long-lived process); no MCP tool. `commit` is not a security boundary and says so. Not showable by a test: that a person, not a script with a pty, is at the terminal (accepted in `requireHuman`).
- **Write-time re-check (Decision 5).** `decideHuman` takes no attempt; the phase check is the engine's `visitFor(..., ["human"])` under the run's lock (`run.ts:1899`, `host.ts:1685-1735`). The TUI's `commit` re-reads the run right before the write and refuses on any difference listed in Decision 5; a rejection written with neither reason nor comments is therefore impossible. A residual window remains between this re-check and the apply; it is the dialog's window, practically unreachable, accepted.
- **The pick is only a request.** What is decided is the `(run, node, attempt)` of the arrived check; a pick that moves meanwhile (`g`, a refresh, the mouse) cannot redirect a pending `y`. Keys and mouse that change the pick or selection are ignored while a question is open or being asked.
- **Attempts in the picker.** The first gate's attempt is `next.waiting.attempt`; the others come from the same `state` read as the session. A gate reworked between two reads makes `prepare` refuse ("look again") and the list is reloaded at once: fail closed, at most one spurious refusal.
- **One confirmation order.** `prepare` returns the ordered questions (the second only for an approval with unavailable changes). The command asks them with `env.confirm`; the TUI walks the same list. `y` is ignored until the check for the same triple arrived; the effect takes its triple from that check, never from `selectedSession` or the pick; the bar closes with a notice when a refresh shows the decision gone. A chunk stops when a confirmation opens.
- **Redaction.** Every run text goes through `plain` before it is shown (question, picker line, card, notice).
- **pipeline-core / local untouched (Principle 4).** The module lives in `cli` with its own refusal class (`UserError` is private to `cli.ts`), mapped in `cli.ts`. The picker reads `also_waiting` and `state`, both public.
- **Stored formats.** None changes: same calls, no `byAgent`, same record; no `v` bump, no fixture. The command passes the reason as given, the TUI trims what it typed.
- **Engine work after a decision:** Decision 3. A resume of a `restarts` pause also starts work in the TUI process (`run.ts:2627-2635`) and registers too. The work after a decision on a run of another checkout runs in this checkout (as in the command); the question says so.
- **Refutation of the task:** refuted if a TUI decision record differs from the command's, or a refusal of `kodel gate` is accepted by the TUI.

## Steps

1. **`gate-decision.ts`.** A `DecisionRun` interface (the part of `LocalRun` used) and its own refusal class. `prepareGateDecision(run, { decision, node?, reason?, expectAttempt?, ignorePendingChange? })` → `{ node, attempt, questions, comments, shown }` or refusal, with the command's order and messages (foreign sentence included in the questions for the TUI; the command keeps its stderr warning). `commitGateDecision(run, prepared, reason, { recheck? })`: without `recheck` it is today's `decideHuman` plus the engine's refusal text; with it, the re-checks of Decision 5. `prepareResume` / `commitResume` likewise. `WORK_WAIT_MS` moves here; the changes fingerprint is exported from `decide-text.ts`.
2. **`cli.ts`** `gate` and `resume` call them without `recheck`; `requireHuman`, `warnIfForeign` (before `refuseWhilePending`), `env.confirm`, `afterDecision` stay; the refusal class is mapped to `UserError`. Output and order unchanged. *(First commit ends here; no `CliEnv` change.)*
3. **Session (`session.ts`, `load.ts`).** `Session.decisions: { kind: "gate" | "pause"; node: string; attempt?: number; prompt: string; command: string }[]`, from `inspect()` (`waiting` first, then `also_waiting`) with the attempt of the first gate from `next.waiting.attempt` and the rest from the same `state`; empty for `pipeline_edit` / `hand_edit`.
4. **Card for a picked gate (`gate.ts`).** `loadRunDetail(source, runId, pick?)` builds the detail for the picked gate (a `Waiting`-shaped value from its prompt, no instructions); the first gate keeps today's path. `detailKey` becomes `id:since:node:attempt`.
5. **Model (`view.ts`).** `Model.picked: Record<runId, key>`; `g` / `G` move it, ignored while a question is open (keys and mouse). `a` / `r` come from the picked decision (`gate`: approve / reject; `pause`: resume) through one helper that replaces the five `NEED_KEYS` reads. In project mode they push `check_decision` and enter an "asking" state (only `q`, Ctrl-C, `Esc` pass). The result carries questions and facts; `y` pushes `decide_gate` / `resume_run` only for a matching check with that check's triple; a missing reason opens `Input` of kind `reason`; `applyInput` stops a chunk when a confirmation opens. `c` / `d` use the picked gate. List row and card head show count and position. Demo keeps `decide()`. The `hand_edit` / `pipeline_edit` notice is reworded.
6. **Performer (`tui/decide.ts`, `run.ts`).** `TuiOptions` gets `checkDecision`, `decide`, `refreshMs` and `quit: { waitMs, graceMs }`; without the functions `a`/`r` say "cannot decide here". It registers `(run, node)` when a commit starts, reloads list and card at once (also after a refusal), drops the card after a write. Quit as in Decision 3; `finish()` keeps stdin and a redraw alive in the wait phase so a second `q` is heard. `tuiOptionsFor(source)` builds the options.
7. **`cli.ts` `tui`** builds the functions from the module and `host()`; `requireHuman()` stays first; `--demo` uses `tuiOptionsFor("demo")`.
8. **Tests** as listed, with the testkit helper `forkOfTwoGates` (built from the fork cases in `fork-join-cli.test.ts` / `elicit-fork.test.ts`) and the existing latch runner.

## Implementation notes (where the code differs from the plan)

- The fork fixtures live in `packages/cli/test/tui-decide.test.ts` itself (copied from `fork-join-cli.test.ts`); no testkit helper was added.
- `tuiOptionsFor(source)` became `decisionOptions(source, tools)` in `tui/decide.ts`; the quit limits are options of `createDecisionTools` (`waitMs`, `stopWaitMs`, `hardStop`), and the loop reads them through `TuiOptions.work`.
- A run that waits for a change of its pipeline (`pipeline_edit`) or a hand edit has no `decisions`, so `a` there names the command; the check-time refusal "a change of the pipeline" is reached by a screen that was read before the file was edited.
- `g` / `G` collide with the diff reader's first/last-line keys only while a diff is open; elsewhere they move the pick.
- Not run by me, as the pipeline's own steps do it: the full suite, the full lint and the build.
- The list row shows `approve ×N` (the need tag with the count) where the plan said `· N decisions`.
- Plan test 10 (`task_dxn6_refusals_reach_the_notice`) is several named tests in `tui-decide.test.ts` (pending change, attempt, decided elsewhere, changed comments, a check that cannot run) and the module tests; plan test 6 is `task_dxn6_unavailable_changes_need_second_yes` on a faked run, plus the module tests. The quit test (plan 16) uses a faked run, not the latch runner on a real run.
- The "one function" test compares the messages the command and the screen give for the same refusals on a real run, and checks by source that both import the module; it does not observe the identity of the functions (no seam was added for that).
- A run shown as running that has a person to wait for (`also_waiting` of its `node` or `running` answer) lists the commands on its card as `Also waiting for you`; the engine words the command (`--node` only when several branches are paused).
- Review round 1 fixed: the confirmation notice is no longer replaced by the "pick is gone" notice after the read that follows a write; a pasted chunk stops whenever the question moves on (`yy`, `yq`); the screen's refusal for a pending pipeline change does not name `--ignore-pending-change`.
- Review round 2 fixed: the card of a picked pause shows that pause (headline, prompt, command, picker line), not the first gate; the key of a decision no longer holds the attempt, and a gate reached again as a new attempt drops an open question in its own words; the loop's catch notices go through `plain`; the performer keeps only the latest few checks and forgets a refused decision when it waits at quit. Not done: control-character fixtures in the approve and reason tests (the neutralising is asserted in the comment and the failing-check tests).
- Review round 3 fixed: a comment being typed (or a deletion being asked) is cancelled when the card it is about changes under it (the picked gate was decided elsewhere, a new wait began), so it cannot be saved onto another gate; a refused write no longer erases the mark of an earlier decision at the same node; the re-check of a resume also refuses a run that is no longer running or paused. These fixes were made after the engine's checks of the last attempt, so the full suite did not run on them; the touched test files (190 tests) and the typecheck did.
