# Fork/join in the run engine (TASK-HRPZ)

## TL;DR

- A pipeline can fork (several edges with the same `from` and `when`) and join (`join: all`). Engine work (`command`, `check`) of branches runs at the same time, several gates can be open at once, and **all open agent steps are listed together** (`steps[]`), so a client that can run subagents works them in parallel and one that cannot does them one by one. The engine is client-neutral: it accepts completions in any order; only the instruction text differs (`agents` config block). A soft claim by token (`pipeline_take_step`) keeps two workers off one step; `pipeline_next_step` stays read-only.
- The join is an ordinary node (normally an agent) that always starts with `feedbacks[]`; its reserved outcome `restart_failed` re-runs failed branches (checked at completion, executed in `route()` after the join's checks). Pauses are per branch (`pauses[]`, resumable whatever the run status), `resume` needs `--node` with more than one pause, `recheck`/`reroute` work inside an open fork (`effects[]`).
- **Format 2 (your choice B):** `RECORD_VERSION` becomes 2 for all new runs. A run of format 1 is refused with a clear `UNSUPPORTED_FORMAT` naming the format; the old beta refuses format 2 by its existing "newer kodel" check. No reader for format 1, no guessing from the shape. The v1 fixtures stay as they are and prove the refusal; new real runs (accepted change, fork) go to `fixtures/formats/v2/`.
- Cost: large; **one PR in four commits**, each green; about 230 small named tests. Risks: the pause/status rewrite, the claim protocol, the shared working tree, lock time with many snapshots, 9 open v1 runs in this repository.
- What the last critique (no blocker, no critical) changed: AGENTS.md and the fixtures README are amended for the one-time format break; `v: 2` is defined for state, journal and `engine.record_version` only; a human-rejected branch is excluded from `restart_failed` by default; repair reaches branches that already arrived failed; a claim survives a node restart; the dialog exemption keys on the claim token, not on `node_slug`; `complete_step.next` never shows a sibling's step; an open format-1 run makes `pipeline_start` refuse instead of starting a second run; the time under the lock and the apply queue get bounds; about 40 more tests, a table with a decision column, and the T-40 id as a gate before commit 1.

## Behaviour change

- Several edges with the same `from` and `when` start their targets together; `join: all` starts when every branch of the fork instance has arrived (any label with an edge to the join). A duplicate `(from, when)` without a `join` is a validation error (the second edge used to be silently ignored; an edge without `when` and one naming the first success label are the same `(from, when)`). Nested forks are refused. A branch cannot route a failure to a node before the fork, and a `human` node in a branch routes `rejected` inside the branch or to the join.
- **Agent steps.** `pipeline_next_step` (read-only, idempotent) returns `node` (the first step) and `steps[]` (every open agent step: prompt, attempt, `result_spec`, `outcomes`, `reentry_feedback`, `workdir`, `taken_by` mark), `execution.mode` and, with `node_slug`, exactly that step. Mode `parallel`: "start one subagent per step; each worker calls `pipeline_take_step` with its slug and uses the `workdir`, keeps the `claim_token`, calls `pipeline_complete_step` with it; on `waiting`, `running`, `done` or `also_waiting` it reports back to you and does not start `kodel wait`"; mode `sequential`: do them one by one. `pipeline_take_step` without a slug takes the next free step. If all open steps are taken, `next_step` answers `running` with `open_steps`, and `wait_s` really waits (it polls the state, with an injectable clock, while claimed agent steps are open). `pipeline_complete_step` never claims another step: its `next` is what the completion left or opened (the completed node's own rework step when the checks failed, the step after it, the steps it forked, the join it filled), otherwise a `running`/`open_steps` summary or `waiting`/`done`; a sibling's step that was open already is never its `node` (see "Notes from implementation"), and `recordServed` does not record a sibling's step as served to that caller. A worker (a call with a `claim_token`) gets only its own rework step or a summary. Results are recorded per step.
- **Status.** `paused` means nothing can move; a branch at a limit pauses only itself. Movable: an open gate, a free agent step, an engine/checks visit that is stale but not yet suspended (so `tick` can restart it). `pauses[]` replaces `pause`. `kodel resume`, core `resume`, the dialog, `next_step` and `kodel wait` look at `pauses.length > 0`, not at the run status. With more than one pause `resume` needs `--node` and names the paused nodes; it gives a fresh budget to that node and the exhausted nodes of its own branch only.
- **A pending pipeline change in a fork** holds every worker's hand-in, as today; command/check branches keep moving. The change shown to the person records the standing visits and pauses (a fingerprint); accept is refused with "the run moved on; look again" when they differ, and `pipeline changes show` recomputes.
- **Doomed fork.** A branch with no route stops only itself. Answers keep serving open steps and say "a branch is dead; finish the open steps; the run ends `failed` when the others have settled"; `kodel status` shows what it waits for. The final reason is one line per dead branch: `branch "<head>" failed at "<node>" (<source>): <reason>`, joined with `; `, in trail order.
- **CLI/next_step.** `waiting` answers list other decisions in `also_waiting`, and `tell_the_person` itself names every waiting decision; `node`/`running` answers carry the text (no `kodel wait` offer unless something waits; `kodel wait` treats any waiting decision or pause as waiting). With several gates `how_to_decide.cli` has `--node`, and `kodel gate` without it is refused. `afterDecision` (`gate`, `resume`, `pipeline changes apply`) waits only for the decided node's own work. `pipeline_complete_step` waits only for the completed node's own checks.
- **Join.** Always starts with `feedbacks[]`; non-fork `reentry_feedback` keeps its text; a join's names every failed branch. A run completing after failed arrivals is flagged (`join_reached.failed`, `report`, `status`).
- **Pipeline change in an open fork.** `recheck`, `restart`, `reroute` work for any branch (`effects[]`); repairing the join's checks or prompt is allowed; the nodes of branches that already arrived (failed ones included) count as reachable through the join of an open fork, so a failed branch's check or prompt can be repaired before `restart_failed`; refused: removing a node where a branch stands or that a paused branch is about to enter, and changing the fork edges or the `join` field of an open fork. A change to a node outside the open section keeps its old rules.
- **Journal and report.** `node_entered` carries `fork`/`branch`; overlap needs no other field (timestamps exist). Events `fork_started`, `branch_settled`, `join_reached`, `step_claimed`, `step_claim_conflict`; journal records are `v: 2`. `report`: `busy_wall_s`, `critical_path` (the chain of attempts from the fork to the join with the longest sum of attempt times, a gate wait counting as its waiting time and a rework attempt counting in its own branch, ties by trail order), overlaps, the flag, and per-visit agent-log byte numbers marked unverified in a fork (including `endedInStep`, which lists every open agent step); `total_s`, `work_s` stay. `status` (text, `--json`, the MCP shape) lists `pauses[]`.
- **Config** `agents: { subagents: auto | yes | no, max_parallel: N, claim_ttl_s: N }`. The MCP contract version is bumped (new tool, new parameters). `AGENTS.md` ("Running a pipeline on this repository") gets the worker rules.

## Risks and invariants

- **1 Untrusted agent / 2 Fail closed.** Checks and the engine decide every step; claims and tokens are advice (a wrong or missing token never refuses a completion; a second completion of a closed step is a no-op and does not re-open it). A join never starts with a missing arrival; a fork with a dead branch can only end `failed`; a join entered after failures is flagged. **Every new refusal is reachable from an agent or human event only** (`agent_completed`, `human_decided`, `resume`, `pipeline_take_step`), never from a `check_finished`/`work_finished` path, where a refused follow-up is dropped by `applyWithRetry` and the branch stalls. `restart_failed`'s verdict at `route()` cannot refuse: if no branch failed by then it routes as an ordinary label with no edge (a validation case) or fails the run with a journaled reason. `enter()` meeting an active node ends the run `failed` with a journaled reason. A `diff` check after a failed snapshot fails its branch.
- **3 Redact.** New texts (`feedbacks`, `branch_settled.reason`, composed run reason, `step_claim_conflict`, `taken_by`, `pauses[].reason`, `also_waiting`, `tell_the_person`, the restarted branch's rejection reason) go through the existing redact paths. State fields (`Visit.claim`, `NodeRun.lastFailures`, `BlockedRoute.feedbacks`) are built from redacted text only; the token is stored hashed. Each redaction test sits in the commit that writes the field.
- **4/5/7 No I/O in core; kinds are adapters.** Logic in `run.ts`, `pipeline.ts`, `next-step.ts`, `report.ts`, `pipeline-diff.ts`; the claim clock is the `now` passed in; the token is generated and hashed by the host; config arrives as options; `join` and the reserved label are generic: one `labelsOf(node)` helper adds `restart_failed` for a node with `join` and a kind with outcomes, and is the only source for validation (exempt from the "outcome needs an edge" rule, refused if listed in `outcomes:`), `next_step`'s `outcomes` and `agent_completed`'s check. `dispatch` stays inside the lock with a deadline per snapshot and one snapshot per fork (the tree is stored under each branch's key), a **total bound of 20 s for one decision's dispatch** plus `runFacts` on a run end (both far below `staleLockMs` = 60 s, after which another process takes the lock; if the bound is hit the remaining gate snapshots are recorded as unavailable like a failed snapshot); a `take_snapshot` failure there is non-fatal. The in-process FIFO queue of `apply` (heartbeats, ticks, `step_served`, agent-log events of all branches) gets a logical bound test too, and `applyWithRetry` is not the only guard: a dropped `check_finished` is re-run by `tick`. Hand-in snapshots: the "two timed-out hand-ins switch patches off" back-off is not applied while another branch is active.
- **6 Humans decide trust.** No new agent-callable decision: `pipeline_take_step` is a claim; `restart_failed` is an outcome of a step the agent already completes; a restarted branch reaches its gate again; `resume`, `ack`, `seal` stay human; `decisions` untouched; the dialog never holds a worker.
- **8 Stored data.** Format 2 (decision 1). `pauses[]` replaces `pause`, `effects[]` replaces `effect`; new optional `forks`, `Visit.fork`, `Visit.claim`, `NodeRun.lastFailures`, `BlockedRoute.feedbacks`; `BlockedRoute`, `Pause` and `NodeRun` carry the `fork` attribution (`{id, branch}`), and `enter(slug, rework, feedback, fork?)` takes it, so a branch re-entered after `resume`, a repair (`restart`, `recheck`, `reroute`) or `restart_failed` still arrives at its join. A kept pipeline snapshot goes through `parseSnapshot` (`canonical.ts:89`), the single entry point; every format-2 snapshot was written by the new rules, so the `pipeline-host.ts` mapping to `STATE_MODIFIED_EXTERNALLY` stays as it is (rule 3), and a later tightening of the fork rules must stay out of the snapshot path (a comment and a test say so). The validator text names the old behaviour ("a second edge with the same `when` used to be ignored"). Fixtures: v1 untouched (hash list untouched); `fixtures/formats/v2/` holds real format-2 runs. The `agents` block is read on the same path as `waitHint()` (reload at each answer, fall back to defaults on error), so a bad value can never fail `pipeline_next_step` for a running run; it is reported when the project config is loaded.
- **Concurrency.** One active visit per node. Heartbeat/owner/takeovers/restarts per `Visit`. `settle` per task key; `waitForRest`/`engineBusy` take the node and also wait while claimed agent steps are open. `recordHandIn` reads its base outside the lock: patches in an open fork may overlap (documented in the docs and `docs/changes.md`). The served-answer hash covers only the per-step, sibling-independent part; `fitServed` can cut `steps`.
- **Known limits (T-40, each with the observation that would refute it):** shared tree (patches, gate changes, `diff` checks see sibling writes; refuted if a gate shows another branch's writes with no note); a snapshot failure in a `diff` check fails that branch (Windows: a file held by a sibling; untestable here); cross-process `STATE_LOCKED` while snapshots are taken, bounded by the deadline, and on Windows `rm` of a lock file another process holds may fail (a Windows run of the concurrent host test with several polling workers is in the gates); agent-log per-visit shares are wrong for parallel siblings and a second end-of-step copy may be skipped after waiting 5 s on the agent-log lock; a soft claim does not stop a determined executor, and two workers on one step both write in the tree, the first completion closing it; a real client starting subagents from `execution.mode` is not testable here (refuted by the journal of a real run with no overlap; a manual check in T-40); the dev pipeline's own fork is a later change.

## Notes from implementation

What the code does where it differs from, or is more exact than, the text above (from the review of the four commits):

- **`pipeline_complete_step.next`.** A linear pipeline behaves as before: the completion answers the successor step (or the completed step's own rework). In a fork the same rule holds for what the completion itself opened: the branches it forked, the join it filled, the next step of its own branch. Only a step of *another* branch that was open already is never the `node` of the answer (it is named in `open_steps` of a `running` summary): `t40_complete_next_never_shows_sibling_step`, `t40_complete_next_shows_own_rework_and_what_the_completion_opened`. A worker (a call that carried a `claim_token`) is stricter: it gets its own rework step or a `running` summary telling it to report back, never a fork's `steps[]` or a successor (`t40_worker_completion_that_opens_steps_gets_a_summary`). After a dialog on a completion call the answer is recomputed with the same completion arguments (`t40_dialog_after_completion_keeps_completion_arguments`).
- **`Visit.spec`** (stored, optional): the pipeline version the engine work in flight was issued under. A `check_finished`/`work_finished` whose `specHash` differs from the run's current version is kept when it matches the visit's issue-time version, so a sibling branch's command in flight survives an accepted change that did not touch it. Documented in `docs/changes.md`.
- **Validator.** A fork on a failure label refuses a branch that is the join itself (it would arrive failed at once and `restart_failed` would run the join as a branch); the machine excludes such a branch from `restartable()` all the same. Every node of a branch must have a way to the join along the branch's own edges (a cycle with no exit is refused, one with an exit is fine). An edge `when: restart_failed` is refused (the engine never follows it).
- **`join_reached` and `joined`** are written only when the join is really entered: a route held back at the join's attempt limit is counted when `resume` or an accepted change lets it in, and that change re-takes the way into the join instead of re-arriving the last branch (`t40_join_reached_only_when_join_entered`, `t40_reroute_of_join_pause_reenters_join_without_rearriving`).
- **`agents.max_parallel`** caps the steps in flight, not the size of an answer (fifth review, 8): with that many steps held, `pipeline_next_step` hands nothing out (a `running` summary with `open_steps` and `queued`) and `pipeline_take_step` refuses a take by slug as well as a take of the next free step (`queued`: nobody holds the step, the cap does); only the holder of a step renews it under the cap: `t40_take_any_honours_max_parallel`, `t40_max_parallel_caps_steps_in_flight`, `t40_take_by_slug_under_the_cap_answers_queued`.
- **`dispatchAll`** takes the snapshots of a decision before it starts the decision's commands, so a command's own writes are never in its `diff` baseline (`t40_host_snapshot_taken_before_commands_of_the_decision_start`).
- **Fixtures.** The `v2/` runs are real runs of the local host (fifth review, 4): `scripts/take-v2-fixtures.mjs` drives `LocalPipelineHost` with the real process executor, git worktrees, prompts recording on (`step_served` records and `served/` files for every step), a build stamped on the host (`engineVersion` `0.1.0`, never `unknown`) and real commits in the scratch repository (a neutral author), so `head`, `tree` and `run_finished.commits` move with the run; only the agent's part (files, completions, the proposal, feedback) and the person's decisions (through the host methods the commands call) are scripted, and `fixtures/formats/README.md` says so for each run. A fourth run (`fork-pause`) pauses a branch at its limit while the sibling arrives and is resumed with `resume(node)`, so `run_paused`/`run_resumed` with a fork attribution and the report's pause count are pinned (`t40_paused_fork_run_fixture_pins_pauses`; the old fork test is `t40_fork_run_fixture_in_v2_shows_forks`, truthfully, since that run never paused). The runs were taken with no `CLAUDE*` variable in the environment, so no agent session of a person is in the repository; the guard test refuses one. `report.work_s` is summed in milliseconds and rounded once, like `busy_wall_s`, so the union never reads above the sum.
- **The claim** lives on `NodeRun.claim`, not on the visit, and survives only an accepted-change restart of an open agent step (`t40_claim_survives_node_restart`): a recheck or a resume comes after the hand-in, where the claim is already released, so there is nothing to carry over. A scoped `engineBusy(node)` deliberately ignores claims; only the unscoped call waits for claimed steps as well.
- **The join's `reentry_feedback`** ("Branches of the fork failed: ...") is given on the fresh entry of the join, decided by comparing `lastFailure` with `lastFailures[0]` by value, never by identity: the host writes the state and reads it back between the entry and the answer (`t40_reentry_feedback_lists_all_failures_after_the_state_was_stored`, and the fork run of `scripts/check-artifact-fork.mjs`, whose two branches both fail once).
- **`resume` of a `total` pause at the join** (a pause without a branch) tops up the join and the nodes outside the branches of the forks that join there; the branches that arrived asked for nothing (`t40_resume_at_join_tops_up_join_and_nodes_outside_its_branches_only`). A pause at a node that is not a join, outside any fork, tops up pipeline-wide as before.
- **Sequential mode** does not send the agent to `pipeline_take_step`: a step it held would not be handed to it again by a plain `pipeline_next_step`, which only says that every open step is held. The held summary says that a holder gets its own step back with `node_slug` (`t40_sequential_rules_do_not_send_the_agent_to_take_its_steps`).
- **`fitServed`** cuts no `steps`: `servedPart` leaves what a step's siblings do out of the served record before it is written, so there is never a `steps` field to cut.
- **A decision that ends the run waits for its patch** (third review, 1). The node-scoped `settle(…, node)` of the host also waits for the end jobs (the run patch and `changes_recorded`): `kodel gate`, `kodel resume` and `kodel pipeline changes apply` return only once they are written, so the process exit that follows loses nothing (`t40_gate_that_ends_the_run_waits_for_its_patch`, `t40_resume_that_ends_the_run_waits_for_its_patch`, `t40_changes_apply_that_ends_the_run_waits_for_its_patch`). `parked` stays unscoped (it counts the whole run's tasks; said in its doc comment).
- **A held-back route into a branch is taken as it is** (third review, 2). `routeEntersBranch` (core, used by the machine and `diffPipelines`): a pause whose blocked route is the fork's own edge into a head, or the join's `restart_failed` into a branch, is lifted by `proceed(blocked)`, like a pause at the join; working it out again from `from` fired the fork a second time beside the open instance and the run ended `failed`. `diffPipelines` never answers `recheck` for such a pause (the fork fired on that verdict and its other branches are going), it answers `reroute` (`t40_reroute_of_fork_edge_pause_enters_head_under_same_fork`).
- **The consecutive limit of a fork on a failure label is judged once** (third review, 3). `fork()` judges `max_consecutive_failures` of the fork node before any head is entered and, at the limit, pauses once with `node` the fork node and `BlockedRoute.heads` (the heads in edge order, `to` the first) and no fork instance yet; `proceed` of that route forks once, into every head, so `resume` (one pause: no `--node` needed), a `reroute` and a `recheck` enter all heads under one instance (`t40_fork_on_failure_at_consecutive_limit_pauses_once`, `t40_resume_of_fork_pause_enters_every_head_under_one_fork`, `t40_repair_effect_on_fork_pause_enters_every_head_under_one_fork`). `diffPipelines` treats every head as standing (`t40_fork_pause_blocks_removing_any_head`) and `kodel resume` waits for every head. The per-head `total` pauses are per node, as before. The core test host now reads the state back through JSON between events, as the real host does.
- **A fork whose join is held back at its attempt limit is open** (fourth review, 1). That pause is the join's and carries no branch, so `isOpen` in `pipeline-diff.ts` also counts a pause whose blocked route enters the fork's join (`blocked.join`); replacing or adding a branch is refused then (`t40_fork_held_at_join_limit_is_open_so_its_edges_cannot_change`). Defensively, `proceed` of a route into a node the pipeline no longer has (a state that still names a branch the spec lost) kills the branch with the reason "node X is no longer in the pipeline" instead of throwing from a check path, and the run ends by the dead-branch rule (`t40_restart_failed_into_a_removed_branch_kills_the_branch_instead_of_throwing`).
- **The last arrival is found by arrival order** (fourth review, 2). `Arrival.seq` (the `seq` of its `branch_settled`, optional in the stored record) orders the arrivals; `tryJoin` takes the greatest, since the keys of `arrived` put an integer-like slug first whenever it arrived (`t40_last_arrival_is_by_arrival_order_not_by_key_order`). Feedbacks, dead-branch reasons and the report were already in branch order and are unchanged; the v2 fork fixture (arrivals without `seq`) still opens.
- **No `reroute` for a route taken as it is while its limit holds** (fourth review, 3). For the join's `total` pause, and a head held back at the fork's own edge or at `restart_failed`, `diffPipelines` offers a `reroute` only when the changed pipeline lets the node be entered once more (`max_attempts` raised); otherwise the pause stays and the effects say nothing, instead of promising that the run goes on and pausing again at once (`t40_change_that_leaves_the_join_at_its_limit_offers_no_reroute`). The `recheck` rule is unchanged.
- **`end()` clears `pauses`** like `active` (fourth review, 4), so a canceled or failed state carries none; every reader (`resume`, `nextStep`, the CLI, the dialog) already keys on the status first (`t40_end_clears_pauses`).
- **The random-schedule test** (fourth review, 5) passes the state through JSON at every event and mixes in accepted (and refused) changes of the pipeline between two valid versions, besides the cancel it had; the injected-bug self-test stays.
- **A decision waits for its own branch's chain** (fifth review, 1 and 6; replaces the fourth review's before/after reading of the standing). The node-scoped wait of the host (`settle`, `waitForRest`, `engineBusy` with a node) follows the branch of the decided node (`inOwnBranch`, core): every visit or job of the same branch, and everything outside any branch (the join and what follows it), is waited for; only a visit of another branch of a fork is left to whoever asks next. So `kodel gate`, `kodel resume` and `kodel pipeline changes apply` return once the whole chain their decision led into is applied, also in a pipeline without a fork, and the exit of the process that follows leaves no command running to be lost and run again (`t40_gate_waits_for_the_chain_its_decision_leads_into`, `t40_resume_waits_for_the_chain_it_leads_into`, `t40_changes_apply_waits_for_the_chain_its_effect_leads_into`, `t40_after_decision_follows_its_own_branch_chain_not_the_sibling`). `kodel gate` no longer diffs the standing before and after the decision: what the decision led into is in its branch by construction, so a node a sibling entered while the person read the question is not waited for (`t40_after_decision_ignores_a_sibling_that_moved_on_while_the_person_read`). The scope is explicit (`WaitScope`, core): the commands use `chain`; `pipeline_complete_step` uses `step` (the completed node's own checks, as before): the server lives on, nothing is lost, and the agent is handed what the completion opened at once instead of after the commands of the branches it forked (`t40_complete_step_waits_only_for_own_checks`, and the dialog tests of a sibling writing while the dialog is open still hold).
- **`pipeline_take_step` shows the waiting change** with the step a worker takes, as `servedPart` says (fourth review, 7; `t40_a_changed_file_is_shown_with_the_step_a_worker_takes`).
- **Dropped tests.** `t40_check_or_work_follow_up_refused_is_not_dropped` was replaced by the `refusedFollowUps` count of `t40_random_schedule_keeps_invariants` (no result of work the run asked for is refused while it goes), and `t40_fit_served_cuts_steps` was dropped: `fitServed` cuts no `steps` (see above).
- **A fork is open while anything of it stands** (fifth review, 2). `isOpen` in `pipeline-diff.ts` is a rule, not a flag: an instance is left only when every branch has arrived and no attempt or pause stands in a branch or at the join; the join's attempt counts until it has been routed on, held back at a limit in any form (its `total` pause with `blocked.join`, a `consecutive` pause on its own rework route or on its way out), since a repair can open it again and judge it anew, and `restart_failed` would enter the branches as the instance names them. The join is shared by the instances of a fork in a loop, so what stands at it belongs to the latest. The random-schedule tests run a join that pauses on its first red check and mix in structural variants (a third branch, the join's attempt limits): a change of the fork's shape is counted refused while open and accepted after, and a new invariant (i) says that an instance something stands in names the branches the current pipeline forks into (`t40_fork_whose_join_is_paused_on_its_own_check_is_open`, `t40_random_schedule_keeps_invariants`).
- **`NodeRun.declared`** (fifth review, 3; stored, optional): the outcome the agent declared for the current or last attempt, set at `agent_completed`, dropped when the node is entered again or the attempt passes. A `recheck` that reopens a closed attempt restores it on the visit, so a join handed in with `restart_failed` whose check was repaired runs its failed branches again instead of finishing `passed` and going on past the join; the same for an ordinary `outcomes:` label (`t40_recheck_of_a_held_join_keeps_its_declared_outcome`, `t40_recheck_of_a_held_step_keeps_its_declared_label`).
- **`kodel pipeline changes apply`** names `--node <slug>` and the paused steps when two or more pauses stay (fifth review, 5; `t40_changes_apply_names_node_when_several_pauses_stay`).
- **The gate note** in `nextStep` takes the attempt of the gate's own visit from the state, as `changesSinceGate` does (fifth review, 7). `waiting.attempt` is always set by the core, so the two never disagreed through the tools; the attempt is now read from one place (`t40_gate_note_uses_the_gate_visits_real_attempt`).
- **Validation** runs the graph rules whenever every node is valid, over the valid edges, so one pass reports a bad edge and what the graph lacks besides; only the fork rules wait for every edge to be valid, since they read the whole shape (fifth review, 9; `t40_one_bad_edge_does_not_hide_the_graph_problems`). `lastArrival`'s comment says truthfully that arrivals without `seq` tie and the later branch wins (fifth review, 10).
- **Suspended work stays suspended** (sixth review, 1). A `work_finished`/`check_finished` or a heartbeat for a visit suspended after too many restarts is a repeat, also while a sibling branch keeps the run `running`; `resume` of its `restarts` pause issues the work again, as before (`t40_late_result_of_suspended_visit_is_a_repeat`). `settle` makes the run robust besides: a `restarts` pause with no suspended visit behind it is dropped (nothing can resume it), and a run with no visit and no pause ends (`failed`, naming every branch that never arrived, or a dead branch as before; else `completed`) instead of staying `paused` (`t40_run_with_nothing_left_ends_instead_of_staying_paused`, `t40_run_with_an_unarrived_branch_and_nothing_left_ends_failed`). The random-schedule invariants say that `running`/`paused` has a visit or a pause and no `finishedAt`, an ended run has one, and every `restarts` pause has its suspended visit; the generator sends heartbeats, replays late results and runs with work that goes stale fast (`t40_random_schedule_with_suspended_work_and_late_results`).
- **A `reroute` names its pause** (sixth review, 2). The effect carries `to` (where the held route was going) and `branch` (stored, optional; effects journaled before have neither and still read), so of several pauses sharing `from` (a join's `restart_failed` into several branches) the change lifts exactly the one the diff judged; the person is told which branch goes on and toward which step (`t40_reroute_lifts_the_pause_the_diff_judged`).
- **A scoped wait takes over only its own work** (sixth review, 3). The `tick` event takes an optional `nodes`; the tick a node-scoped `waitForRest` makes now and then is limited to the caller's own work, so `kodel gate`/`resume`/`changes apply` never start a sibling's orphaned command in the process that is about to exit (`t40_scoped_wait_never_takes_over_a_sibling_command`). Defensively `afterDecision` waits, within the same deadline, for whatever else this process still runs.
- **A worker's `running` answer** says to report back like `waiting`/`done` (sixth review, 4; `t40_running_answer_to_a_worker_says_report_back`). **`pipeline_take_step` is not idempotent** (5): a take without a token claims another step; the description says to keep the first token (`t40_contract_version_and_surface_snapshot` pins the hints of every tool).
- **A join started again by an accepted change** is told the change and its branches' failures (sixth review, 6; `t40_restart_of_join_keeps_the_failed_branches_list`). **The cap after a completion counts every held step**, a sibling's too (7; `t40_completion_answer_counts_sibling_held_steps_against_the_cap`). **Refused follow-ups fail a scenario** (8): the runner fails on a follow-up the engine refused while the run went, unless the scenario declares `allowRefusedFollowUps` (`t40_scenario_fails_on_a_follow_up_refused_while_the_run_goes`); no existing scenario needed the opt-out.
- **`takeStep` answers the step asked for** when a worker that holds one takes another with the same token, and `renewed` is judged for that step (sixth review, 9; `t40_take_of_a_second_step_with_the_same_token_answers_that_step`). **The hand-in note** uses the journal: another branch's node that moved since this attempt was entered makes the tree shared, also when nothing else is active at the hand-in (10; `t40_hand_in_note_when_a_sibling_wrote_and_arrived_before_it`); `t40_hand_in_backoff_not_applied_in_open_fork` now shows the last branch still noted and the join, alone, backed off.
- **Docs and messages** (sixth review, 11-12): `pipeline-spec.md` says `none` with `next.running.queued` for a take without a slug and `queued` by slug, and the workers' rules (AGENTS.md, `parallelRules`) say to stop and report on `taken`/`queued`/`none`; README documents the `agents:` block; `fixtures/formats/README.md` says what the served files hold (`[REDACTED:high-entropy]…` workdirs, untouched); the e2e fork test runs the artifact under `node` when one is on the PATH. `kodel report` with only unreadable runs names their format; the meta-format refusal no longer advises removing the run; a `state.json` that is not a JSON object reads as modified; `inspect` answers with the same `agents` options as `nextStep` (`t40_report_without_run_picks_latest_readable`, `t40_meta_version_unchanged_and_messages_distinct`, `t40_state_json_that_is_not_an_object_reads_as_modified`, `t40_inspect_answers_with_the_agents_config_like_next_step`).
- **A passed join does not hold its fork open** (sixth review, 13). A pause on a route out of the join counts for `isOpen` only when the join failed (its rework or failure route); a join that passed and whose way on is held at the next node's limit leaves the fork, so its shape may change (`t40_join_that_passed_and_is_held_at_the_next_limit_does_not_hold_the_fork_open`; the earlier refusals still hold).
