# Do not orphan a run in flight when the run-state format changes (TASK-5ZCN)

## TL;DR

- **What is done.** A run is pinned to the stored format it started with (`state.v`). Each stored format has one **codec** in `pipeline-core`: `decode` to the engine's model, `encode` back, and `capabilities` (what the format can hold). The engine reads and **writes** each run in its own format: a format-1 run goes on in format 1 to the end (old MCP, new MCP, new CLI), a new run is written in the current format. `status`, `report` and history read every run, finished ones too.
- **Format 1 is one family** (decided): every writer of `v: 1` (early builds, the published beta, `main` at `12f8578`) wrote a subset of the `12f8578` shape, so one decoder reads all and no run is refused for the build that wrote it. The decoder is **closed**: the audit lists every key any v1 writer emitted, and a key outside the list is "cannot read" (found before the merge by scanning real runs). In a format-1 run the engine does not set `Visit.spec` (decided; capability `visitSpec: false`).
- **Way up, by a person.** When a format-1 run is asked to hold what its format cannot (a fork, a second pause), the call is refused **before anything is written** and the agent is told to offer the person the human-only command **`kodel migrate <run>`** (like `gate`, `ack`, `seal`), or to leave the run with the format-1 limits. Same PR (decided). The upgrade is one way and is refused for a run whose state is not trusted.
- **Enforced in core.** `decide()` returns the **encoded** state and records, or a refusal; every store (the local one and the testkit engines) writes what it is given. A kept pipeline is parsed by the rules of the format it was written in, so `kodel migrate` cannot make an old snapshot unreadable.
- **What the eighth critique changed:** closed top-level keys instead of pass-through (no unredacted carry, no fail-open on unknown keys); the encoder also checks the invariants between fields (`status` and `pause`, size of `active`); migrate refuses a modified or untrusted state; the consistency rule is "highest `v` in the journal or any `run_migrated`"; the two meanings of "no kept pipeline" are told apart; byte-order promises and the `proposals apply` warning are cut; the testkit engines are named; one more fixture holds a failed check from the real engine.
- **Cost and risk.** Medium-large: `formats/` (~250 lines), ~12 engine edits, `migrate` (~100 lines), about 40 tests or groups (7 renamed), three fixtures made by the real `12f8578` engine, AGENTS.md. One PR, two commits (A, B). In CI "the old engine reads what the new writer wrote" is shown only by the manual check; the other limits are in the release note.

## Decisions needed

**Decided by the person (recorded):** (1) duplicate edges: old way for snapshots already kept; new text always meets the current rules; (2) a format-1 run is a limited writer, plus `kodel migrate` and a hint; (3) runs with no kept pipeline still block `pipeline_start`, cancel is a separate task; (4) the limits of older engines that a new engine cannot lift are accepted and go in the release note; (5) ids `t41_`, T-41; (6) format 1 is one family; (7) one PR; (8) `Visit.spec` is not set for format 1.

**Open, with defaults (say if you want otherwise):**

1. **Finished format-1 runs and `pipeline_start`.** Today a finished v1 run is skipped (refused, passed over) and `pipeline_start` for its task starts a new run. Once v1 is readable it answers as a finished v2 run does (a baseline test on a v2 fixture records the value first; the v1 test copies it; expected "terminal, a restart is needed"). (a, default) Accept: "not blocked" means "behaves as v2". (b) Keep the old skip for finished v1 runs (a special case that stays forever).
2. **What `kodel migrate` takes.** (a, default) Open runs (`running` or `paused`) with a kept pipeline, in any supported older format; it refuses a finished run, a sealed run, a run with a fresh heartbeat, a pending change, a run already in the current format, a run with no kept pipeline, a state whose hash is **modified** or **unknown on this machine** (open it once with `status`, then try again), and a state with a key the current format does not know. Command only, no `decisions.dialog` form. (b) also finished runs: no use, and it rewrites history.
3. **Deny rules.** The agent may not edit `.claude/settings*.json`. (a, default) The final report gives you `Bash(*kodel* migrate*)` and `Bash(*main.ts* migrate*)` to add next to the rules for `gate`, `ack`, `seal`, `resume`; the terminal check guards the command meanwhile and is tested; the deny rule itself is not in the PR and not tested.

Stated, not questions: new runs are always written in the current format. `decode` of a supported format stays for good; `encode` can be retired by an explicit decision after the first release. **Follow-up tasks created with `task_create` after approval, keys in the final report; done for "propose" means the task exists:** cancel a run; **the proposal of this task**: accept both `format` and `version` in pipeline files (error if both are given and differ), with the reasoning that `version` is already the renamed key (`692305a`) and a user file with `format:` now fails with a generic unknown-key error; old-engine tooling (recorded before/after pairs, `scripts/check-old-engine-reads.mjs`). The unmerged TUI branch (`tui-prepared-merge`) is named in the final report only. The *snapshot* reader accepts `format:` only if the audit finds a supported fixture whose snapshot uses it.

## Behaviour change

- **Old runs go on.** A format-1 run that was going when the package was updated can be continued by the new MCP after a restart, by any new CLI (`gate`, `resume`) and by the old MCP still running (within the limits below). All write format 1; the journal of a run stays of one version unless the person migrates it.
- **New runs** start in the current format (2). While an old MCP runs beside a new one it cannot open them, and its `pipeline_start` for the same pipeline and task throws.
- **A format-1 run meets what it cannot hold** — a pipeline with a `join` proposed or accepted into it, a second pause, a fork attribution: refused before anything is written, `UNSUPPORTED_FORMAT_FEATURE`: "this run is written in run-state format 1, which cannot hold X; ask the person whether to upgrade it (one way: the older kodel will not read it afterwards) with `<command>`; only a person can run it; or leave the run as it is". `<command>` is the concrete command the server knows from how it was started when that is a plain path or an `npx`/`bunx` launch, else `kodel migrate <run>` with the note that an older `kodel` on the PATH may not have it; no home path reaches the agent (`scrubHome`). `pipeline_propose_change` with a `run_id` is refused at **propose** time. `pipeline_take_step` on a format-1 run answers `none` with a note that this run has no claims, no hint. A person who accepts a `join` pipeline with `pipeline proposals apply` outside a run finds each open v1 run of it waiting on a change it cannot apply; `discard` or `restore` lets it go on (release note).
- **`kodel migrate <run>`** (human-only, a real terminal, a confirmation): prints what changes (format N to the current one, one way, the old kodel will not read it, **close every older session on this run first**, including one idle at a gate or in an agent step, which send no heartbeat; a declared outcome is now kept after a failed check), takes the run lock, re-reads and re-hashes under it, refuses a modified or unknown hash, rewrites `state.json` in the current format, writes the trusted hash on the normal path, and appends `run_migrated {from, to}`. If it cannot replace `state.json` (an older process holds it, common on Windows) it says to close the older session and leaves the run as it was. Earlier journal lines are untouched; `served/`, `changes/`, `reports/`, `snapshots.json` are untouched. After it the run forks and claims like any current run and its old snapshots still parse as before.
- **History and status** read format 1 and 2 alike. `pipeline_start` for the task of an open run does what v2 does today for an open run of that task (a baseline test fixes it; no new start semantics); a finished format-1 run: open decision 1; a different task or pipeline starts a new run and leaves the old one untouched.
- **Runs from before pipelines were kept in versions** (`meta.json` format 1: no kept pipeline, no `specs/`) have `state.v: 1` and are read and listed; they are **not continued by any engine**: refused with today's text ("written before pipelines were kept in versions ... finish it with the kodel that started it") and still block `pipeline_start` for their task (decision 3). This is the one case where a `state.v: 1` run is refused, said in AGENTS.md. A run whose `specs/<hash>` is missing or edited stays "modified", as today.
- **Limits accepted (decision 4, release note):** the strict project config of the older engines: `12f8578` refuses `agents:`, the beta also `decisions`, `history`, `prompts`, `executor`, `tool_log`, `storage`, `project_id`; the beta does not see `storage: home` runs; no lock retry on Windows in either (transient `EPERM`, and a rename can fail while the old process holds the file); after the new engine starts a format-2 run for a pipeline and task, the old `pipeline_start` for that pair throws; an older `kodel wait` that watches a migrated run is not covered; an older process that writes back a cached state after a migrate yields a run the new engine refuses as inconsistent; the beta may not read a run after the new engine wrote it; one run can be decided under two rule sets for the plain fixes the audit does not pin (status derivation, `usage` per branch among them).

## Risks and invariants

- **1 Untrusted agent / 2 Fail closed.** The format is chosen by `state.v` only; unknown or newer is refused ("upgrade kodel"). **The v1 decoder is closed and is the union of what every `v: 1` writer wrote**: top-level and nested keys and values (statuses, pause reasons, effect kinds, outcome kinds, `usage`, `agentLog`, `served`, `head`, `commits`) come from the audit, and a key or value outside it, or a key of a **later** format (`pauses`, `forks`, `claimEvents`, `lastFailures`, `BlockedRoute.feedbacks`, ...) in a `v: 1` file, is "cannot read" (status and report still list the run by its raw header). This leaves nothing to carry through unredacted. Before the merge `scripts/list-v1-runs.mjs` opens every real v1 run (`.kodel/runs`, `~/.kodel/projects/*/runs`, `.kodel/worktrees/*/.kodel/runs`) with the decoder, so a key from an intermediate dev build is found before a user finds it; this is an item of the PR checklist. The current format decodes nested objects leniently. The hash of the bytes read is computed in `packages/local` and goes with a refusal; the host checks it before it says "format" where the audit finds that order wrong; a changed file is "modified" also when it no longer parses. **State and journal must agree:** a state whose `v` is lower than the highest `v` in its journal, or lower than the format named by any `run_migrated` line, is "cannot read" (a cached v1 state written back after a migrate), never read as v1. `meta.json` is not a selector of the state format (the one meta check is the continue refusal above).
- **The v1 encoder is an allow-list with no droppable field, and it checks the invariants between fields** that `12f8578` relies on: `status` is `paused` iff a pause is set, `active` holds at most one visit, a suspended visit only under a `restarts` pause; a state that breaks one is refused (these arise only with forks). Fields the engine sets unconditionally are handled one by one in the key table: `Visit.spec` (not set in v1), `effect.spec`, `standing`, `claimToken`, `nodes` on tick, `node` on resume. **`pipeline_accepted`:** zero effects are written as `{kind: "none"}`, one as itself, more than one is refused (the audit confirms `diffPipelines` returns one effect without a `join`). A key table for the state types **and for the journal event union and its payloads** is kept complete by the compiler (`satisfies Record<keyof ...>`; the gate that shows it wrong is `typecheck`), and a runtime test shows that a key outside the table makes the encoder refuse; Rule 5 is checked by both.
- **Encode first, enforced in core.** `decide()` returns `{ state, journal, encoded: { state, journal } }` or a refusal; `encoded` is plain JSON values. Every store that persists a run writes `encoded`: the local host (`host.ts:1676-1682`) and the testkit engines (`memory-engine.ts`, `local-engine.ts`); a host-only check would leave enforcement to each store, which is why it is not enough. Encoding of the state and **all** records happens before the first write, so a refusal on any record leaves state, trusted hash and journal untouched (tested end to end through the host). A failing `appendJournal` after a successful `writeState` is the existing behaviour, documented by a test as a known gap. A background event (`tick`, heartbeat, check or command completion, agent-log and usage capture) in a run with no `join` cannot reach a refusal: the only fields a refusal needs come from forks or claims; this is shown end to end with a v1 run that holds a pending hand-edited `join` receiving a tick and a heartbeat; if one does anyway it is refused like any call (nothing written) and the run reports it on each status until the person acts (`migrate` or leaving it). Order of keys is not promised (the old engine reads JSON). Redaction: the journal after encode (tested with a planted secret); state is not redacted today and holds no passed-through text.
- **Snapshots by their own format.** The format a kept snapshot was written in is the `v` of the **first** journal line that names its hash (`run_started.spec`, `pipeline_accepted.to`), read **only after the journal's integrity check has passed** (an unchecked journal is "cannot read", a test); none found is "cannot read". The snapshot reader applies that format's rules (first-wins for a duplicate edge without a `join`). New text meets the current rules plus the run's `pipelineFeatures` on every path (file, propose, apply). **Decided coupling:** snapshot parse rules are keyed to the record version of the introducing journal line, so a tightening of the pipeline parser that would make an old snapshot unreadable must keep the old rule for snapshots written before it and is therefore a record-version bump (a separately versioned snapshot parser is the alternative if this hurts; it is not built). The canonical form (the edge sort in `routingOf`, `canonical.ts:54-63`) is not pinned: if the audit finds an affected supported pipeline, it goes in the release note.
- **Engine behaviour that follows the run's format** is the named short list: `keepsDeclaredAfterFailedCheck` (false in v1) and `visitSpec` (false in v1); the stale-result rule uses `state.specHash` as `12f8578` did (a differential case recorded by the real engine). Everything else since `12f8578` is a plain fix applied to every run (accepted limit). The audit lists the readers and writers of run files, among them the history features that fire in the background of a v1 run (agent-log capture, usage recording and `usage_failed`, served records, `tool_log`): each has its own record versions or is read tolerantly, and `migrate` rewrites only `state.json` and appends to the journal.
- **`kodel migrate` and Principle 6.** A human-only CLI command, refused without a terminal (a non-TTY spawn of the built binary exits non-zero with no write), with a confirmation, in the AGENTS.md lists of commands (the "Do not run" list, the "Humans:" paragraph and the Layout line for `packages/cli`), **not** an MCP tool and not in `decisions.agent`. `run_migrated` is built only by `HumanRun.migrate` in `local`; `PipelineService` has no method that takes a raw event (a test iterates the tool registry and calls the engine entry point without the human flag). Under the run lock it re-reads and re-hashes, refuses a fresh heartbeat (the engine's staleness default; the idle-gate and agent-step cases rest on the confirmation text: untestable, said), refuses `modified` and `unknown` hashes, writes the trusted hash through `stage` then `set`, and stops on an unknown key. A crash before the state write leaves the run as it was; between the writes it leaves a current-format run without the mark, and a second call says "already current" and **appends the missing mark** (tested).
- **3 Redact / 4,5,7 Core without I/O / 6.** Codecs, capabilities, `readRunState(text, hash)` and the event live in `pipeline-core`; the command and files in `local` and `cli`; the engine asks `capabilities`, never a number. `UNSUPPORTED_FORMAT_FEATURE` is a new code in `errors.ts` and `docs/changes.md`; `CONTRACT_VERSION` is bumped the way the fork merge bumped it; `decide()` gains `encoded` (a package API change Kodel Server must follow; it may always run the current format); `how_to_upgrade` text is local. A repository-specific pointer is in AGENTS.md, not in engine text. The executor's `record_version` is written only into `run_started`, so it needs no change for a continued run.
- **8 Stored data (AGENTS.md rewritten, step 6; flagged to the person as a change to a Principle; most of these edits are consequences of the decisions above).** Principle 8 and the preamble: the **journal** is the history and is only appended to; `state.json` is the run's current state, no longer "never edited" but written in the format the run lives in; `kodel migrate` is the one allowed change of that format, by a person. Rule 1: "ships a reader **and writer** for the previous format, a real fixture, and tests that open and continue it". Rule 2: snapshots as above, with the coupling. Rule 3: unsupported / cannot read / modified stay three errors; "upgrade or migrate" becomes "upgrade, or `kodel migrate` where it applies". Rule 4: "may break freely" only for a format no published version wrote and no supported run uses; the refutation that replaces T-40's is "a user outside this repository reports a run of a supported format refused or changed (a run from before pipelines were kept in versions excepted)". The T-40 exception paragraph is withdrawn. **Rule 5 (new):** a change of a stored format ships `decode`, `encode`, `capabilities`, a real fixture in `v<N>` or `v<N>-<tag>` and the round-trip test; a new field is a compatible addition only if an engine of the same version that ignores it decides every step the same way and an older engine that writes the run back and drops it leaves the newer engine deciding the same way (no mechanical form; a rule of review), otherwise the version is bumped; a `decode` is never removed, an `encode` only by decision after the first release.
- **Fixtures.** Made by the real `12f8578` engine in a temporary worktree (the one hard dependency, done **first**; if it cannot be built offline, work stops and asks you): (1) an open run at a `human` gate; (2) a run paused with an accepted pipeline change, with the engine's own decision on a result that carries the old spec hash (the differential case for decision 8); (3) a run with a failed check and a declared outcome, over a pipeline with a duplicate edge, with the engine's own routing result. The README records the commit and the take command. They are scripted-agent runs of the main variant: the early-build family is read through `fixtures/formats/v1/` (finished runs) and the **published beta has no fixture** (no tag in the repository); the beta is covered by the audit and by the scan above. A pending change shown by the old engine is simulated by the new writer (the pending change is stored as YAML source, and `effects` and `standing` are worked out on read, `host.ts:1198`; the `standing` check is optional, `run.ts:2217`).
