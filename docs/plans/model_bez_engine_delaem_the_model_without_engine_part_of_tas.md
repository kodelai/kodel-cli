# `model` on an agent node without `engine` (the rest of TASK-WKJ4)

## TL;DR

- Done: a node `kind: agent` may say `model: sonnet` with no `engine`. The agent that drives the run is told to run the step on that model: in a subagent when it works the step itself, in a **worker started on that model** when the project works a fork's open steps in parallel. `kodel report` then shows, per attempt, the model **requested** (`declared`, read from the pipeline snapshot the attempt ran under), the models **observed** (`derived`, from the agent's logs) and `match`, `mismatch` or `not observed`.
- Cost: medium, **one PR in three commits** (field and instruction; the mark for steps worked in one session; the observation for steps a fork's workers did). The last commit can be dropped without losing anything the task asks for; the plan has a fallback.
- Risky: observed models come from files the agent's session can write; helper subagents and the host's own model count too; the worker observation leans on the worker's call being in its log in time. So the mark is information and says `not observed` whenever it cannot be sure.
- What the second critique changed: a run of format 1 now **refuses** a model step like it refuses engine steps (its kept copy would be unreadable to the beta); a worker's models are written on the journal event of its hand-in (always written), not on the usage record (which may write nothing), and a worker step never falls back to the pooled usage; steps not done by a worker in a run that had workers are `not observed`; the worker answer mode follows the worker flag in every answer; the work for the test rigs is listed.

## Decisions needed

None is open. You decided these in the chat; each is written with its context so the plan reads alone.

1. **Where the requested model comes from.** Context: the report compares "what was asked" with "what was seen"; it needs the first value. Options: (a) the copy of the pipeline Kodel keeps with every run, the one in force when the attempt began; (b) a new field in the journal when the step is handed out (unreliable: skipped when `history.prompts` is off, capped, and a format change). **Decided: (a).**
2. **What counts as a match.** Context: you write `sonnet`; the log says `claude-sonnet-5-5`. Rule: lower-case both, drop a trailing `[...]` of the id, split at `-` and `:`; the name must contain a letter; it matches when its segments are a contiguous run of the id's segments. So `sonnet` matches `claude-sonnet-5-5`; `claude-sonnet-5` matches it (a version prefix is meant) but not `claude-sonnet-4-6`; a bare `claude` matches every Claude id (accepted, in the docs). The line says **by host** when the host session's own model at that attempt matched (checked first, so a host and a subagent both on the family read `by host`), **by subagent** when something else did, **by worker** for a step a worker did; with `history.executor` off the host's model is unknown and the label is left out. A helper subagent that Claude Code starts on its own (Explore) cannot be told from the one that did the step; the docs say so. **Decided: this rule.**
3. **Strict check (a step that fails on a mismatch).** Context: the mark is information only; `docs/history.md` says usage "never feeds a check, a route or a gate", and a check would fail good steps whenever a usage pass is `busy`. **Decided: none** in this task; a check would be its own decision lifting that rule.
4. **`observed-hook`.** Context: the task lists it as a source; the hook payloads Kodel receives carry no subagent model. **Decided: not used.** The task is delivered as "`declared` and `derived` only"; the docs and the PR description say so, and record that the source can be added when a host sends such a field.
5. **Forks.** Context: in a fork the coordinator starts one worker per open step and they run at the same time. A worker cannot start a subagent on another model, and the usage count credits everything new in all logs to the step being handed in. **Decided: make them work**: the coordinator is told per step which model to start that step's worker on, the worker is told it runs on that model, and the models of a step a worker did are read from that worker's own log (the one holding its `pipeline_complete_step` call for that node and attempt) and written on the journal event of the hand-in. If that log is not found the mark is `not observed (worker_not_found)`. **Fallback, recorded in the plan:** if the worker observation proves unreliable in practice, the third commit is dropped and a run with workers shows `not observed (workers_in_run)`; the instruction side stays.
6. **Where the mark is shown.** **Decided: `kodel report` only.** The MCP history tools and the TUI show nothing; added later, they say `unverified`.
7. **Size.** **Decided: one PR** (three commits inside it).

Notes: `fresh_context` is allowed together with `model`; in the text a worker gets, the fresh-context sentence is left out (a worker is a fresh subagent already). The decision id `T-43` and the test prefix `t43_` are proposed and to be confirmed against the local decision log before the build; the decision-log entry (test plan, refutation criterion) is written with it and attached to the PR description, since the notes folder is not in the repository.

## Behaviour change

- A pipeline author may write `model: sonnet` on an agent node that has no `engine`. Today `pipeline_start` refuses it. The value must look like a model name (letters, digits, `.`, `_`, `:`, `[`, `]`, `-`; at least one letter; at most 128 characters); with `engine` any non-empty string, as now. A run of format 1 refuses a pipeline with a model step in a proposal or an accepted change, with `UNSUPPORTED_FORMAT_FEATURE` and the offer of `kodel migrate`, the way it refuses engine steps.
- A step worked on its own (one step, or a fork worked one by one): the agent is told to do it in a subagent on that model (in Claude Code the Agent tool's `model`; the family name such as `sonnet` is advised), to send what it found as it is, and to say so if it cannot choose a subagent's model.
- A fork worked in parallel: the coordinator's text gets one line per open step that has a model: "start the worker for step `S` on the model `X`"; the steps listed in the answer carry the same wording, never the single-step sentence. Every answer to a worker (the step it takes, a renewal, and its own step handed back after a failed check) says "you run on `X` for this step; if you are not on `X`, say so in your summary" and never tells it to start a subagent.
- `kodel report` shows, per attempt of such a step: `model sonnet requested, seen claude-sonnet-5-5 (match, by subagent)`, or `mismatch`, or `not observed (<reason>)`. The mark changes no route, check, gate or cost number.
- A step with `engine` is unchanged (its model is not a request for a host subagent and is not marked). A model step is not an engine step: it runs with `KODEL_ENGINE_STEPS` off.

## Risks and invariants

1. *Untrusted input.* The model the agent states of itself is never read (the tools take no such argument). Observed ids come from the session log and the subagents' logs; the agent's session can write those files, so a hostile agent can fool the mark. It is information and decides nothing.
2. *Fail closed.* The mark closes and refuses nothing. It says `mismatch` only on clear evidence, `not observed` otherwise, with one of these reasons: `usage_missing` (usage off, no record for the attempt, an empty models map, or any entry in the run's `usage.failed` or a cursor `behind`: the record is not clean), `unknown_id` (an `other` id among the observed), `unsupported` (a run of format 1, or a client that is not Claude Code), `no_snapshot`, `worker_not_found`, `workers_in_run`. For a step worked in one session `match` also needs the clean record, because use of one step can land in the next. The over-downgrade (one `usage.failed` entry, which names no attempt, downgrades every such step of the run) is deliberate and pinned by a test.
3. *Redaction.* The requested value is checked against the model pattern; observed ids pass `MODEL_ID` (others fold to `other`). No free text reaches the unredacted state.
4. *No I/O in the core.* The match rule and the mark are pure functions in `pipeline-core` that take the journal, the state and a map of requested models. The kept snapshots and the logs are read by the host and the usage code in `packages/local`.
5. *Traits.* The log reads use the readers the usage code already uses.
6. *Humans decide trust.* The field is in the pipeline, which only a person's command puts in place.
7. *Kinds are adapters.* `NodeHandler` gains an optional `requestedModel(params)` (undefined for a node with `engine`) and an optional `ctx` argument for `instruction(params, ctx)` with `mode: "single" | "coordinator" | "worker"`; `next-step.ts` and the host ask the handler and never match on a kind. Both members are optional, so a server that registers its own kinds is unaffected.
8. *Formats.*
   - Requested model: nothing stored (decision 1). Rule 2: `model` without `engine` loosens a user-file rule, so no kept copy becomes unreadable; the new pattern applies only without `engine`, which no earlier copy can hold.
   - **Format 1 refusal.** A pipeline feature `model` is added to the format-2 capabilities only; the three places that already refuse `join` and `engine` for format 1 (the proposal and the person's apply in `host.ts`, and `acceptPipeline` in `run.ts`) refuse a model step too, through a predicate on the handler's `requestedModel`, not on `engine`, so the engine-steps switch is not involved. Reason: the kept copy would be a pipeline the published beta, still supported for format 1, refuses (T-41).
   - **Worker observation stores one optional field**, `worker_models` (sorted, unique, at most `MAX_MODELS_PER_RECORD`, each checked against `MODEL_ID`, else `other`), on the journal event `agent_completed` of a step a worker handed in. It is written by the host in `completeStep` (it does not ride on the usage record, so the caps, `busy`, `isEmptyDelta`, `passes` and the cursors are not involved). Per your note of 2026-11-03 run format 2 is unreleased and may be amended in place; rule 5's test holds anyway (an engine that ignores or drops the field decides every step the same way). A golden fixture `fixtures/formats/v2-model/` (a fork with two workers) is opened with `status` and `report`; a test strips the field and compares the decisions; the v2 codec round trip is tested. `docs/run-formats.md` gets the amendment and says an older dev build keeps a field it does not know, and refuses only a pipeline it cannot parse.
   - Older builds (the published beta, a server from another checkout) refuse a pipeline, and so a kept copy, with `model` and no `engine`; a dev build says "was modified" for a copy it cannot parse, as for any new pipeline key. The docs say so.
9. *The usage count can be late or partial.* It runs inside `completeStep` under the lock before the step is judged, so the record is in the state when the report is built. A pass credits everything new in the session and its subagent logs to the step handed in; a `busy` or `unreadable` pass leaves its use for the next step; the clean-record rule keeps that from showing as a false mark. Cost and token totals are unchanged by this task.
10. *Worker observation, step by step.*
    - A step is a worker's when the journal says so: `step_claimed` for that node and attempt (and the hash on `agent_completed`). Never from the presence of `worker_models`. A worker step whose models are missing is `not observed (worker_not_found)`; it never falls back to the pooled usage.
    - The host finds the worker's log among the subagent logs of the candidate sessions (`subagentLogs`), by the step's `pipeline_complete_step` call (`hasStepCall`'s match on `run_id`, `node_slug`, `attempt`). The **main log is never searched**: a coordinator that takes a step with a token, a worker that is another top-level session or a `kodel agent` session, and a log that is not a candidate all give `worker_not_found` (the docs list what counts). A call found in two logs is ambiguous: `worker_not_found`.
    - The models are those of the assistant responses **between the worker's previous `pipeline_complete_step` call (or the start of its log) and this one**, so a worker kept for a retry or a later step does not mix attempts, and responses written after the call (its closing report) are not counted. A log over a size bound (4 MiB) is `worker_not_found`.
    - The wait: a hand-in with a claim token looks in the worker logs first and has its **own** bounded wait (2 s, polling like `awaitStepCall`), outside the log-copy lock, never sharing the pass's wait. The search reads a tail of at most 64 logs and stops at the first match; the total read is bounded (8 MiB).
    - **Pooled usage after workers.** The worker's closing responses are credited by the pooled count to whatever step is handed in next. So in a run that had any worker hand-in, a model step **not** done by a worker is `not observed (workers_in_run)`; the pooled rule is used only in runs without workers (and the sequential fork, `agents.subagents: no`, has none).
11. *Served records.* The text a step carries depends on its mode, so a step listed to the coordinator and then taken by a worker is served with two different prompts: two `step_served` events and two files instead of one. The caps (`MAX_SERVED_PER_ATTEMPT` 20, `MAX_SERVED_EVENTS` 500) are far above this; a test checks a fork of many model steps does not hit them.
12. *Server contract.* The instruction, the handler hooks and the snapshots live in `pipeline-core`; the observation lives in `packages/local`. A server-backed run shows `not observed (unsupported)`; the docs say so.
